## 计算器实际回答的问题

给定预算、需要新抽到的角色/武器份数以及起始卡池状态，估计“这些资源足不足以抽齐全部目标”。

它在浏览器本地进行蒙特卡洛模拟，不请求服务器计算，不读取游戏账户或抽卡记录。一次计算固定模拟 100000 次。每次都从相同输入状态开始，抽到目标全部完成才结束，再用预算筛选成功样本。

目标数字表示本次需要抽到的份数，不直接表示命座。没有角色时，0 命填 1、2 命填 3、6 命填 7；已有 0 命且只需升到 2 命，则新增目标为 2。程序没有已有命座/精炼等级输入，星辉模型也不会自动根据已有命座调整。

角色与武器名称仅参与选择、显示、高亮和重复角色检查，不改变抽卡概率，也不校验所选物品是否同池。

## 数据与调用路线

```text
app/page.tsx
  ├─ SimulatorStateProvider：保存两个主题共用的输入、计算状态和报告
  ├─ CitlaliInterface / OdetteInterface：显示输入、触发各自的 startSim
  │    └─ lib/simulator.ts：runSimulation → 多次 runOneSimLogic
  │         └─ 返回每次总抽数、星辉和物品份数
  └─ 两个 Interface 各自汇总报告，再写入共享 report
       ├─ 预算内成功率
       ├─ 原始总抽数柱状图与分位数
       ├─ 平均抽数、平均返还及净消耗
       └─ 抽齐目标时的收获组合
```

共享状态文件也实现了一个 `startSim`，但当前两个界面的按钮调用的是各自局部的 `startSim`。因此统计与预算计算实际上重复存在三份。

## 一次模拟的规则

### 角色池

1. 先抽齐角色 A，再抽齐角色 B；如果某个目标为 0，跳过该目标。
2. 开始时读取角色垫抽和大保底。角色 A/B 共用角色池保底及捕获明光计数状态。
3. 每抽五星概率为 `0.006 + max(0, 本轮累计抽数 - 73) × 0.06`。前 73 抽为 0.6%，第 74 抽为 6.6%，第 90 抽超过 100%，实际必出。
4. 大保底时五星必为当前目标；否则按小保底规则判断。
5. 捕获明光计数初始值固定为 1。普通小保底胜利使计数减 1，最低为 0；失败使计数加 1，并开启大保底；计数为 3 时下一个小保底强制胜利并重置为 1。大保底不改变计数。
6. 出五星后重新累计五星垫抽，继续直到当前目标完成。

捕获明光是本项目采用的计数模型。初始计数现在可以通过界面设置为 0～3，默认值仍为 1；之后的计数更新规则不变。以上描述说明代码如何执行，不代表已独立核实最新游戏机制。

### 武器池

1. 完成角色部分后开始武器部分，先定轨武器 A，再定轨武器 B。
2. 五星概率为 `0.007 + max(0, 本轮累计抽数 - 62) × 0.07`。前 62 抽为 0.7%，第 63 抽为 7.7%，第 77 抽超过 100%，实际必出；当前公式不是到第 80 抽才强制出金。
3. 无命定值时，75% 概率出两把 UP 中的一把，之后各以 50% 选中；因此定轨武器和另一把 UP 各占 37.5%，常驻占 25%。
4. 未抽到定轨武器会获得 1 点命定值，下一金直接获得定轨武器。
5. 歪到另一把目标武器也计入库存，因此可能提前完成武器 B 的部分目标。
6. A 达标后改定轨 B，清空命定值；所有武器目标完成后结束。

武器大保底和命定值均从默认状态开始，没有对应的起始输入。

### 四星与星辉近似

- 先判断五星，没有五星才判断四星。
- 两种池子的四星模型相同：前 8 抽条件概率 6%，第 9 抽 66%，第 10 抽及以后 100%；出四星清零四星计数。
- 每个四星以各 50% 概率返还 5 或 2 星辉，不具体模拟四星角色、武器或已有命座。
- 首次获得目标五星角色给 0 星辉，重复获得时给 10，已累计拥有 7 份后再获得给 25。
- 所有常驻五星角色被合并为同一个 `Std`，并假定最初已拥有 1 份。这会影响返还估算。
- 每个五星武器固定返还 10 星辉。
- 代码变量 `stardust` 实际表示星辉，而不是游戏中的星尘。

## 预算与统计

有效预算：`已有粉球 + floor(已有原石 / 160)`。

不计返还时，一次成功的条件是：`总抽数 <= 有效预算`。

计返还时，当前成功条件是：`总抽数 - floor(最终总星辉 / 5) <= 有效预算`。

最终成功率为成功样本数除以 100000。程序使用 `Math.random()`，正式运行没有固定随机种子，所以重复计算会轻微变化。50% 附近，10 万次样本的标准误约为 0.158 个百分点；这只反映抽样波动，不包含概率模型和返还近似造成的偏差。

报告中的项目：

| 项目 | 当前含义 |
| --- | --- |
| 大字成功率 | 预算足以完成全部目标的样本比例，可选择计入星辉近似 |
| 消耗柱状图 | 所有样本的原始总抽数，分为 40 个区间；不会因为勾选返还而变成净消耗图 |
| 累积概率分布 | 排序后的原始总抽数的 10%、30%、50%、70%、90%、99% 分位值 |
| 最欧、最非 | 这 10 万次样本的最小、最大值；不是数学上的最低成本或绝对保底上限 |
| 模拟平均总消耗 | 总抽数均值 |
| 白板理论总期望 | 角色目标份数 × 93.46 + 武器目标份数 × 66.5，固定参考公式，不参与模拟或成功率判断 |
| 每金平均成本 | 平均抽数除以输入目标份数，没有把歪出的金或额外目标武器计入分母 |
| 平均返还、净消耗 | 所有完成目标样本的返还均值，以及平均抽数减平均返还抽数；即使没勾选返还也显示 |
| 预计返还、共多少抽 | 利用报告的平均返还率作几何级数估算，不是逐抽资金余额模拟 |
| 详细收获组合 | 抽齐所有目标后的库存组合，最多显示前 15 项，不是预算用完时的收获 |

模拟按每批 5000 次运行，用 `setTimeout` 在批次之间让出浏览器主线程。它没有使用 Web Worker；较大的目标可能仍导致界面在一批计算期间卡顿。

## 后续修改需要注意的发现

### 优先处理：星辉预算判断使用了未来返还

当前判断直接扣除抽齐目标后的全部星辉，没有逐抽检查当时能否支付下一抽。最后一抽获得的星辉也会用于“支付”最后一抽，产生不可能的成功样本。

可重复边界：0 粉球、0 原石、角色目标 0、武器 A 目标 1、武器垫抽 79，勾选返还。核心函数返回 1 抽和 10 星辉；判断变成 `1 - floor(10 / 5) <= 0`，成立。但预算为 0 时无法先进行这一抽。应按抽前资金余额判断，或记录每条路径所需的最低起始预算。

### 优先处理：输入与已有报告可能不对应

报告没有保存计算时输入快照。修改名字、目标、预算或返还开关后，旧报告不会清空或重算；但报告中的名字、目标文案、每金成本分母和顶部返还估算会读取当前输入。计算期间输入也未禁用，可能在旧计算完成时把结果展示给新的输入。

应保存计算参数快照并用于报告展示，或在输入变更时标记结果过期。

### 优先处理：目标与预算缺少完整校验

目标输入的 `min=0` 不等于点击普通按钮时会自动执行表单校验。当前处理函数没有统一要求非负整数、有限值及合理上限。实际调用验证：目标 0.5 会抽成 1 份；目标 -1 会被跳过。粉球也可接受小数，垫抽夹在范围内但未取整。极大目标可能让主线程长时间运行。

### 统计含义与固定参考值

- “详细收获组合”来源于所有完成目标的样本，因此纯角色目标通常会出现目标组合 100%，即使大字预算成功率很低。这是统计对象不同，不应解释为预算内收获。
- 勾选返还只改变大字成功率，图表和分位数仍展示原始总抽数，应让文案明确口径。
- “最非保底记录”是样本最大值，不能当作理论保底。
- “每金平均成本”实际按目标份数计算，并非按所有五星数量计算。

### 维护与界面

- 两份约 900 行的主题界面高度重复，再加共享状态中的汇总函数，修改规则/校验/报告时容易只改到其中一处。建议让状态/统计成为单一实现，界面负责展示。

- `false &&` 包裹的旧背景、标题和浮动按钮仍大量保留；当前视频列表被硬编码为空，尽管 background.json 中有视频。

- 根 tsconfig 和 ESLint 目录规则会包含 iOS 源码副本，后续主项目与快照分离时应明确检查边界。
